Основные компоненты многозвенной клиент-серверной архитектуры

| Компонент                     | Назначение                                                                 |
|-------------------------------|---------------------------------------------------------------------------|
| **Клиентское приложение**     | Интерфейс для взаимодействия пользователя с системой (например, веб-браузер или мобильное приложение). |
| **Веб-сервер (Frontend)**     | Обрабатывает HTTP-запросы, отдаёт статический контент и передаёт динамические запросы бэкенду.        |
| **Сервер приложений (Backend)**| Выполняет бизнес-логику, обрабатывает данные и взаимодействует с базой данных или другими сервисами.  |
| **База данных**               | Хранит, управляет и предоставляет данные по запросу сервера приложений.                               |
| **API (REST/gRPC/GraphQL)**   | Обеспечивает стандартизированное взаимодействие между клиентом, сервером и другими сервисами.         |
| **Кэш-сервер (Redis, Memcached)** | Ускоряет доступ к часто используемым данным, снижая нагрузку на базу данных.                         |
| **Брокер сообщений (Kafka, RabbitMQ)** | Обеспечивает асинхронную обработку задач и взаимодействие между микросервисами.                     |
| **Микросервисы**              | Независимые сервисы, выполняющие конкретные функции, что улучшает масштабируемость и гибкость.       |
| **Балансировщик нагрузки (Nginx, HAProxy)** | Распределяет запросы между серверами для повышения отказоустойчивости и производительности.       |
| **Сервер аутентификации (OAuth, JWT)** | Управляет безопасным доступом пользователей к системе.                                             |

| Параметр                | «Горячий» резерв (Hot Standby)                          | «Холодный» резерв (Cold Standby)                     |
|-------------------------|-------------------------------------------------------|-----------------------------------------------------|
| **Определение**         | Резервная система активна и синхронизирована с основной, готова к немедленному переключению. | Резервная система отключена или требует ручного запуска/настройки после отказа основной. |
| **Готовность**          | **Высокая** (работает в реальном времени).          | **Низкая** (требует времени на активацию).        |
| **Синхронизация данных**| **Постоянная** (данные реплицируются в реальном времени или с минимальной задержкой). | **Отсутствует** или требует ручного обновления (например, резервные копии). |
| **Время переключения**  | **Секунды/миллисекунды** (автоматическое переключение). | **Минуты/часы** (зависит от скорости развёртывания и настройки). |
| **Стоимость**           | **Высокая** (требует дополнительных ресурсов для работы резерва). | **Низкая** (ресурсы не используются до момента отказа). |
| **Плюсы**              | – Минимальный простой системы.<br>– Автоматизация восстановления.<br>– Подходит для критичных систем (например, банки, телеком). | – Дешевле в эксплуатации.<br>– Проще в обслуживании.<br>– Подходит для некритичных данных. |
| **Минусы**             | – Дорогое решение.<br>– Сложность настройки синхронизации.<br>– Избыточность ресурсов. | – Длительное время восстановления.<br>– Риск потери данных между резервными копиями.<br>– Зависимость от действий администратора. |


1. **Примеры использования**:
   - **Горячий резерв**: Серверы баз данных (PostgreSQL Streaming Replication), кластеры Kubernetes.
   - **Холодный резерв**: Резервные копии файловых архивов, инфраструктура для аварийного восстановления (DR).

2. **Компромиссные решения**:
   - **Тёплый резерв (Warm Standby)**: Частичная готовность (например, сервер запущен, но не обрабатывает трафик). Баланс между стоимостью и скоростью восстановления.

3. **Критерии выбора**:
   - **Горячий резерв**: Если стоимость простоя системы превышает затраты на резервирование.
   - **Холодный резерв**: Если допустимы длительные простои и данные не критичны в реальном времени.
